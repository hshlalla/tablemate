# TableMate — 기반 리서치 & 초기 세팅 설계

- 작성일: 2026-08-01
- 상태: 승인됨 (사용자 승인)
- 다음 단계: writing-plans 스킬로 구현 계획 수립

## 배경

TableMate는 데이팅과 맛집을 결합한 서비스다. 기존 데이팅 앱과의 차별점은 다음 세 가지다.

1. **함께 먹을래** — 맛집 예약부터 매칭 상대와 실제로 만나 식사하는 흐름까지 하나로 연결
2. **신뢰도(온도) 시스템** — 당근마켓의 매너온도처럼, 데이트 후 상대를 평가해 신뢰 점수를 누적. 특히 "사진과 실물이 다름" 같은 항목을 포함해 프로필 사진 신뢰도 문제를 완화
3. **멀티플랫폼** — iOS(App Store), Android(Google Play), 웹을 동시 서비스

전체 제품은 다음 5개 서브프로젝트로 나눠 순차적으로 스펙·계획·구현한다. 이 문서는 **1번(기반 리서치)**만 다룬다.

1. **기반 리서치** ← 이 문서
2. 아키텍처 기반 (모노레포 구조, 배포 전략)
3. 핵심 데이팅 기능 (프로필, 매칭, 채팅) — 베이스 리포 커스터마이징
4. 맛집 결합 기능 ("함께 먹을래": 예약 + 동반 식사 플로우)
5. 신뢰 시스템 (온도 평가, 매너 평가, 사진 불일치 신고)

## 이번 서브프로젝트의 범위

- 데이팅 앱 베이스 리포 선정 및 자체 저장소로 이전
- 베이스 리포 보안/코드 품질 감사
- 맛집 씨드 데이터 파이프라인 구축 (로컬 DB에 데이터 채우기까지)
- 이후 서브프로젝트가 밟고 설 수 있는 "로컬에서 실행되는 최소 상태" 확보

**범위 밖:** 매칭 로직 커스터마이징, "함께 먹을래" 기능, 신뢰도 시스템, 실제 배포/스토어 등록, 모노레포 구조 확정(서브프로젝트 2에서 다룸)

## 검토한 대안과 결정

### 데이팅 앱 베이스 리포

| 후보 | 라이선스 | 스택 | 완성도 |
|---|---|---|---|
| **helloharendra/Complete-Dating-App** (채택) | MIT (상업적 이용 명시) | Flutter + FastAPI + PostgreSQL + Redis + WebSocket | 스와이프 매칭, 실시간 채팅, 인증, 관리자 대시보드 구현됨. 단 스타 29·커밋 11개로 검증도가 낮음 |
| shubhamhackz/dating_app | MIT | Flutter (프론트만) | UI 스캐폴드 수준, 백엔드 없음 |

**결정:** Complete-Dating-App을 채택한다. 매칭/채팅/인증 백엔드를 처음부터 구현하지 않아도 되는 이점이, 원래 선호했던 NestJS 대신 FastAPI(Python)를 쓰게 되는 트레이드오프보다 크다고 판단했다. FastAPI도 프로덕션급으로 충분히 검증된 스택이다.

**후속 조치 필요:** 원 리포는 관리가 뜸하고 검증도가 낮으므로, fork 유지가 아니라 코드를 새 저장소로 이전해 독립적으로 발전시킨다. 업스트림에 의존하지 않는다.

### 맛집 데이터 소스

| 후보 | 라이선스 | 비고 |
|---|---|---|
| Yelp Open Dataset | 학술/개인용만 허용, **상업적 이용 불가** | 초기에 고려했으나 제외 |
| **Overture Maps Places** (채택) | CDLA Permissive v2.0, 상업적 이용 명시 허용 | 전세계 5,900만+ POI, Meta/Microsoft 등이 기여 |
| OpenStreetMap 직접 추출 | ODbL, 상업적 이용 가능하나 파생 DB 공유 의무(share-alike) 있음 | Overture가 라이선스 조건이 더 가벼워 우선 채택 |

**결정:** Overture Maps Places 데이터셋을 씨드 데이터로 사용한다. 실제 출시 시점에는 예약 가능 여부·실시간 영업시간 등을 위해 Google Places API 등 유료 공식 API로 보강이 필요하다는 점을 스펙에 명시해둔다.

## 아키텍처 개요

- **프론트엔드:** Flutter (iOS+Android+웹 단일 코드베이스)
- **백엔드:** FastAPI (Python) + SQLAlchemy
- **DB:** PostgreSQL (사용자/매칭/채팅 데이터 + 맛집 씨드 데이터)
- **캐시/실시간:** Redis + WebSocket (채팅)

## 작업 내용

### 1) 리포 이전 & 보안 감사

- Complete-Dating-App 코드를 `tablemate` 저장소로 복사, 독립 히스토리로 전환
- 감사 체크리스트:
  - JWT 발급/검증 로직, 토큰 만료·리프레시 처리
  - 비밀번호 해싱 방식 (bcrypt/argon2 여부)
  - SQL 인젝션/입력 검증 (SQLAlchemy 사용이 기본 방어이나 raw query 여부 확인)
  - Redis/WebSocket 연결의 인증 여부 (인증 안 된 소켓 연결 허용 여부)
  - 하드코딩된 시크릿/API 키 존재 여부
  - 관리자 대시보드 권한 검증 (일반 사용자가 접근 가능한지)
- 감사에서 발견된 이슈는 이번 서브프로젝트 내에서 수정하거나, 심각도가 낮으면 서브프로젝트 3(핵심 데이팅 기능)으로 이월해 계획 문서에 기록

### 2) 맛집 데이터 파이프라인

- Overture Maps Places 데이터(Parquet, 공개 S3 버킷)에서 음식/레스토랑 관련 카테고리만 필터링
- 초기 씨드 데이터는 **한국(서울)** 지역으로 한정한다. 이는 개발/테스트 편의를 위한 것이며, **실제 출시 타겟 시장은 여전히 글로벌(미국 등)**이다. 출시 전에는 실제 출시 지역 데이터로 교체·확장이 필요하다는 점을 README/스펙에 명시해둔다
- PostgreSQL로 적재하는 배치 스크립트 작성
- Overture/OSM 기여자 attribution 표기 요건을 앱 내 어디에 어떻게 넣을지 문서화 (CDLA Permissive v2.0 요구사항)
- 이 데이터가 "씨드/개발용"이며 실시간 영업 정보가 아님을 코드 주석 또는 README에 명시

### 3) 산출물 확인 기준

- `flutter run`으로 앱이 로컬에서 기동
- FastAPI 백엔드가 로컬에서 기동, 기본 인증(회원가입/로그인) 동작
- PostgreSQL에 맛집 씨드 데이터가 적재되어 쿼리 가능
- 보안 감사 체크리스트 결과 문서화 (발견 이슈 + 조치 여부)

## 리스크 / 열린 질문

- 씨드 데이터(한국)와 실제 출시 타겟(글로벌)이 다르므로, 서브프로젝트 4(맛집 결합 기능) 착수 시점에 반드시 출시 지역 데이터로 교체해야 함 — 잊지 않도록 이 문서와 README에 명시
- Complete-Dating-App 감사 중 구조적으로 재작성이 필요한 부분이 발견되면 일정에 영향 — 발견 즉시 사용자에게 보고
- FastAPI 채택으로 인한 스택 비일관성(원래 NestJS 선호)은 서브프로젝트 2(아키텍처 기반)에서 재확인 필요
