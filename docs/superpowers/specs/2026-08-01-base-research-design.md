## 배경

TableMate는 데이팅과 맛집을 결합한 서비스다. 기존 데이팅 앱과의 차별점은 다음 세 가지다.

1. **함께 먹을래** — 맛집 예약부터 매칭 상대와 실제로 만나 식사하는 흐름까지 하나로 연결
2. **신뢰도(온도) 시스템** — 당근마켓의 매너온도처럼, 데이트 후 상대를 평가해 신뢰 점수를 누적. 특히 "사진과 실물이 다름" 같은 항목을 포함해 프로필 사진 신뢰도 문제를 완화
3. **멀티플랫폼** — iOS(App Store), Android(Google Play), 웹을 동시 서비스

전체 제품은 다음 5개 서브프로젝트로 나눠 순차적으로 스펙·계획·구현한다. 이 문서는 **1번(기반 리서치)**만 다룬다.

1. **기반 리서치** ← 이 문서
2. 아키텍처 기반 (모노레포 구조, 배포 전략)
3. 핵심 데이팅 기능 (프로필, 매칭, 채팅) — 베이스 리포 커스터마이징
4. 맛집 결합 기능 ("함께 먹을래": 예약 + 동반 식사 플로우)
5. 신뢰 시스템 (온도 평가, 매너 평가, 사진 불일치 신고)

## 이번 서브프로젝트의 범위

- 데이팅 앱 Flutter 프론트엔드 신규 구현 (UI 구조는 오픈소스 프로젝트를 시각적/구조적 참고자료로만 활용, 코드 복사 없음)
- 데이팅 앱 백엔드 신규 구현 (NestJS + PostgreSQL, 회원가입/로그인/기본 프로필/스와이프 매칭/채팅 골격)
- 맛집 씨드 데이터 파이프라인 구축 (로컬 DB에 데이터 채우기까지)
- 이후 서브프로젝트가 밟고 설 수 있는 "로컬에서 실행되는 최소 상태" 확보

**범위 밖:** 매칭 로직 고도화, "함께 먹을래" 기능, 신뢰도 시스템, 실제 배포/스토어 등록, 모노레포 구조 확정(서브프로젝트 2에서 다룸)

## 검토한 대안과 결정

### 데이팅 앱 베이스 리포 — 재검증 결과

실제 GitHub API로 파일 트리와 원본 소스(README, pubspec.yaml)를 직접 확인한 결과, "포크해서 백엔드까지 그대로 쓸 수 있는" 수준의 오픈소스 데이팅 앱은 존재하지 않았다.

| 후보 | 라이선스 | 실제 검증 결과 |
|---|---|---|
| helloharendra/Complete-Dating-App | MIT (README상) | **기각.** 백엔드 코드가 리포에 아예 없음. README가 광고하는 `flutter_app/`+`fastapi_backend/` 구조, `flutter_bloc`/`dio`/`socket_io_client` 의존성이 실제와 다름. 실제 코드 대부분은 의약품 배송 이커머스 템플릿(vendor/cart/checkout/payment)이고 데이팅 화면은 일부만 얹혀 있음. README 하단은 사실상 개인 컨설팅 영업 페이지 |
| shubhamhackz/dating_app | MIT | UI 스캐폴드만 있고 백엔드 없음 |
| wybieralski/DateMe | **라이선스 파일 없음 (기본 저작권 — 무단 복제 불가)** | `lib/main.dart` 등 소수 파일로 이뤄진 소규모 개인 프로젝트. 백엔드 없음. 라이선스가 없어 코드를 그대로 가져다 쓸 수 없고, 화면 구조를 눈으로 보고 참고하는 용도로만 사용 가능 |
| Faiz-rhm/Flutter-Dating-App | 미확인 | 스타 17개 수준의 소규모 프로젝트, 상세 미검증 |

**결정:** 백엔드를 포함해 신뢰할 만한 오픈소스 베이스가 없으므로, **Flutter 프론트엔드와 백엔드 모두 처음부터 새로 구현**한다. UI 구조는 DateMe 등 공개 리포의 화면 흐름을 시각적으로 참고만 하되(로그인 → 홈/디스커버 → 채팅 → 프로필 탭 구조 등), 코드는 복사하지 않고 직접 작성한다 (DateMe는 라이선스가 없어 코드 재사용 자체가 저작권 문제가 될 수 있음).

이 결정으로, 원래 선호했던 **NestJS + PostgreSQL** 백엔드 스택을 그대로 쓸 수 있게 되어 서브프로젝트 2에서 우려했던 스택 비일관성 문제도 자연히 해소된다.

### 맛집 데이터 소스

| 후보 | 라이선스 | 비고 |
|---|---|---|
| Yelp Open Dataset | 학술/개인용만 허용, **상업적 이용 불가** | 초기에 고려했으나 제외 |
| **Overture Maps Places** (채택) | CDLA Permissive v2.0, 상업적 이용 명시 허용 | 전세계 5,900만+ POI, Meta/Microsoft 등이 기여 |
| OpenStreetMap 직접 추출 | ODbL, 상업적 이용 가능하나 파생 DB 공유 의무(share-alike) 있음 | Overture가 라이선스 조건이 더 가벼워 우선 채택 |

**결정:** Overture Maps Places 데이터셋을 씨드 데이터로 사용한다. 실제 출시 시점에는 예약 가능 여부·실시간 영업시간 등을 위해 Google Places API 등 유료 공식 API로 보강이 필요하다는 점을 스펙에 명시해둔다.

## 아키텍처 개요

- **프론트엔드:** Flutter (iOS+Android+웹 단일 코드베이스), 신규 작성
- **백엔드:** NestJS (TypeScript) + TypeORM (또는 Prisma), 신규 작성
- **DB:** PostgreSQL (사용자/매칭/채팅 데이터 + 맛집 씨드 데이터)
- **인증:** 자체 JWT 발급 (bcrypt 해싱), 처음부터 보안 기준을 반영해 설계 — 기존 리포 감사가 아니라 신규 구현이므로 "감사"가 아닌 "설계 기준 준수"로 대체

## 작업 내용

### 1) 데이팅 앱 최소 골격 신규 구현

- NestJS 백엔드: 회원가입/로그인(JWT), 기본 프로필 CRUD, 스와이프(좋아요/패스) 기록, 매칭 성사 판정(양방향 좋아요), 매칭된 유저 간 기본 채팅(REST 폴링 또는 WebSocket 중 하나를 최소 구현으로 선택 — 계획 단계에서 확정)
- Flutter 프론트엔드: 로그인/회원가입 화면, 스와이프 카드 UI(디스커버), 매칭 목록, 기본 채팅 화면 — DateMe 등의 화면 흐름을 참고하되 코드는 직접 작성
- 보안 설계 기준: 비밀번호는 bcrypt 해싱, JWT는 만료 시간 설정 + 리프레시 토큰, 입력 검증(NestJS `class-validator`), 시크릿은 환경변수로 분리하고 저장소에 커밋하지 않음

### 2) 맛집 데이터 파이프라인

- Overture Maps Places 데이터(Parquet, 공개 S3 버킷)에서 음식/레스토랑 관련 카테고리만 필터링
- 초기 씨드 데이터는 **한국(서울)** 지역으로 한정한다. 이는 개발/테스트 편의를 위한 것이며, **실제 출시 타겟 시장은 여전히 글로벌(미국 등)**이다. 출시 전에는 실제 출시 지역 데이터로 교체·확장이 필요하다는 점을 README/스펙에 명시해둔다
- PostgreSQL로 적재하는 배치 스크립트 작성
- Overture/OSM 기여자 attribution 표기 요건을 앱 내 어디에 어떻게 넣을지 문서화 (CDLA Permissive v2.0 요구사항)
- 이 데이터가 "씨드/개발용"이며 실시간 영업 정보가 아님을 코드 주석 또는 README에 명시

### 3) 산출물 확인 기준

- `flutter run`으로 앱이 로컬에서 기동, 로그인/회원가입/스와이프/매칭/기본 채팅이 실제로 동작
- NestJS 백엔드가 로컬에서 기동, 인증 API 및 매칭 API가 테스트로 검증됨
- PostgreSQL에 맛집 씨드 데이터가 적재되어 쿼리 가능
- 참고한 오픈소스(DateMe 등)에서 코드를 그대로 복사한 부분이 없는지 확인

## 리스크 / 열린 질문

- 씨드 데이터(한국)와 실제 출시 타겟(글로벌)이 다르므로, 서브프로젝트 4(맛집 결합 기능) 착수 시점에 반드시 출시 지역 데이터로 교체해야 함 — 잊지 않도록 이 문서와 README에 명시
- "기존 리포에서 시작"이라는 원래 목표가 이번 리서치로 무산되었으므로, 데이팅 핵심 기능(서브프로젝트 3)의 개발 기간이 최초 예상보다 늘어날 수 있음 — 계획 수립 시 반영
- 채팅을 WebSocket으로 구현할지 REST 폴링으로 최소 구현할지는 아직 미정 — 구현 계획(writing-plans) 단계에서 확정
